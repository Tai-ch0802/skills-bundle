# 腦力激盪與溝通協議

> **強制要求：** 用於複雜/模糊的需求、新功能、更新。

---

## 🛑 蘇格拉底閘門 (強制執行)

### 何時觸發

| 模式 | 動作 |
|---------|--------|
| 沒有細節的「建置/建立/製作 [某物]」 | 🛑 提出 3 個問題 |
| 複雜的功能或架構 | 🛑 實作前先釐清 |
| 更新/變更請求 | 🛑 確認範圍 |
| 模糊的需求 | 🛑 詢問目的、使用者、限制條件 |

### 🧠 記憶檢查 (2026.5.13 — 提問前)

> 在提問前，檢查是否存在過去的背景脈絡：

```
0. 檢查記憶 — .agents/memory/MEMORY.md 是否存在？
   → 是：讀取索引。靜默應用相關的過去決策。
          跳過已在記憶中回答的問題。
   → 否：進行標準的蘇格拉底閘門。
```

### 🚫 強制要求：實作前提出的 3 個問題

1. **停止 (STOP)** - 不要開始寫程式
2. **檢查 (CHECK)** - 閱讀 `.agents/memory/` 了解此主題的過去背景脈絡
3. **詢問 (ASK)** - 至少提出 3 個問題（跳過已透過記憶回答的問題）：
   - 🎯 目的：你要解決什麼問題？
   - 👥 使用者：誰會使用這個？
   - 📦 範圍：必備功能 (Must-have) 與加分功能 (nice-to-have) 分別是什麼？
4. **等待 (WAIT)** - 得到回應後再繼續
5. **儲存 (SAVE)** - 腦力激盪後，儲存關鍵決策：`/remember [決策]`

## 🧠 動態問題生成

**⛔ 絕對不要使用靜態模板。** 閱讀 `dynamic-questioning.md` 了解原則。

### 核心原則

| 原則 | 意義 |
|-----------|---------|
| **問題揭示後果** | 每個問題都與架構決策相關 |
| **背景先於內容** | 先了解全新開發/新功能/重構/除錯等背景情況 |
| **最小可行問題** | 每個問題都必須能排除某些實作路徑 |
| **生成資料，而非假設** | 不要猜測——提出附帶權衡考量 (trade-offs) 的問題 |

### 問題生成過程

```
1. 解析請求 → 擷取領域、功能、規模指標
2. 辨識決策點 → 阻礙性 vs. 可延遲
3. 生成問題 → 優先順序：P0 (阻礙性) > P1 (高槓桿) > P2 (加分功能)
4. 帶有權衡考量的格式 → 是什麼、為什麼、選項、預設值
```

### 問題格式 (強制要求)

```markdown
### [優先順序] **[決策點]**

**問題：** [清晰的問題]

**為什麼這很重要：**
- [架構上的後果]
- [影響：成本/複雜度/時間表/規模]

**選項：**
| 選項 | 優點 | 缺點 | 最適合 |
|--------|------|------|----------|
| A | [+] | [-] | [使用情境] |

**如果未指定：** [預設值 + 理由]
```

**如需詳細的特定領域問題庫和演算法**，請參閱：`dynamic-questioning.md`

## 進度報告 (基於原則)

**原則：** 透明度建立信任。狀態必須可見且可採取行動。

### 狀態板格式

| 代理 | 狀態 | 目前任務 | 進度 |
|-------|--------|--------------|----------|
| [代理名稱] | ✅🔄⏳❌⚠️ | [任務描述] | [% 或計數] |

### 狀態圖示

| 圖示 | 意義 | 用途 |
|------|---------|-------|
| ✅ | 完成 | 任務成功完成 |
| 🔄 | 運行中 | 目前正在執行 |
| ⏳ | 等待 | 受阻，等待依賴項 |
| ❌ | 錯誤 | 失敗，需要注意 |
| ⚠️ | 警告 | 潛在問題，不構成阻礙 |

## 錯誤處理 (基於原則)

**原則：** 錯誤是清晰溝通的機會。

### 錯誤回應模式

```
1. 承認錯誤
2. 解釋發生了什麼事（對使用者友善）
3. 提供具體解決方案及權衡考量
4. 請使用者選擇或提供替代方案
```

### 錯誤類別

| 類別 | 回應策略 |
|----------|-------------------|
| **通訊埠衝突** | 提供替代通訊埠或關閉現有通訊埠 |
| **缺少依賴項** | 自動安裝或請求許可 |
| **建置失敗** | 顯示特定錯誤 + 建議修復方法 |
| **不明確的錯誤** | 詢問細節：螢幕截圖、控制台輸出 |

## 完成訊息 (基於原則)

**原則：** 慶祝成功，指引後續步驟。

### 完成結構

```
1. 成功確認（簡短慶祝）
2. 完成事項的摘要（具體）
3. 如何驗證/測試（可執行的）
4. 後續步驟建議（主動）
```

---

## 溝通原則

| 原則 | 實作 |
|-----------|----------------|
| **簡潔** | 沒有不必要的細節，切入正題 |
| **視覺化** | 使用表情符號 (✅🔄⏳❌) 以便快速掃描 |
| **具體** | 「大約 2 分鐘」而不是「等一下」 |
| **替代方案** | 卡住時提供多種路徑 |
| **主動** | 完成後建議下一個步驟 |

---

## 反模式 (避免)

| 反模式 | 原因 |
|--------------|-----|
| 在理解之前就跳到解決方案 | 在錯誤的問題上浪費時間 |
| 不提問就假設需求 | 產出錯誤的結果 |
| 第一個版本過度工程化 | 延遲價值交付 |
| 忽略限制條件 | 建立無法使用的解決方案 |
| 「我認為」之類的用語 | 不確定 → 改用詢問 |
